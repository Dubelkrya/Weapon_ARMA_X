# Пристрелка АК74М от Blender до рабочих дальностей

Дата фиксации: 24 октября 2026 года. Руководство описывает настройку нашего АК74М и порядок переноса метода на другое оружие Arma Reforger. Пользователь подтвердил работу сначала 100 и 200 м, затем набора остальных девяти режимов. Это практическое подтверждение набора, а не протокол измерения кучности на каждой дистанции.

Рабочий результат получился после согласования четырёх вещей: геометрии и шарнира целика, направления вылета, положения целика в существующей анимации и положения оружия относительно финальной камеры ADS. Одного изменения Range X или запуска генератора для этого оказалось недостаточно.

## 1. Что где находится

Корень игрового addon определять через `agent/scripts/addon_path.py`; ожидаемый ID проекта — `ARMSTPLATFORMWeapons`. Дальнейшие пути указаны относительно этого корня.

| Основной АК74М | `Prefabs/Weapons/Russian/Rifle/AK74/armst_Rifle_AK74M.et` |
| Ближайший родитель | `Prefabs/Weapons/Rifles/AK74/ARMST_AK545_415_base.et` |
| Вариант с оборудованием | `Prefabs/Weapons/Russian/Rifle/AK74/armst_Rifle_AK74M_full.et` |
| Итоговая модель | `Assets/Weapons_RUS/AK74m/ak74m_hinge_aligned_test.fbx` и `.xob` |
| GUID итогового XOB | `E27B0C94A63F185D` |
| Магазин основного префаба | `Prefabs/Weapons/Magazines/Russian/5x45/AK74/armst_Magazine_545x39_AK_30rnd_PP.et` |

Название модели осталось экспериментальным, но именно этот XOB указан в основном префабе на дату фиксации. Не выбирать модель только по имени файла.

Резервные копии, расчёты и отчёты хранить в `Weapon_ARMA_X/artifacts/`, инструкции — в `docs/guides/`. В игровой addon добавлять только нужные ему ресурсы. При редактировании соблюдать [контракт префабов](../../agent/SAFE_PREFAB_EDITOR.md).

## 2. Что менять и для чего

| Элемент | Назначение | Когда его менять |
|---|---|---|
| Геометрия мушки и прорези | Видимая линия прицеливания | Если ошибочна сама модель; до окончательной пристрелки |
| Ось и bind-положение `w_sight` | Траектория движения целика | Если вращение не соответствует реальному шарниру |
| Веса кожи | Какие вершины следуют за костью | Если планка деформируется или движется неправильно |
| `barrel_chamber`, `barrel_muzzle` | Опорные трансформы ствола | Только при доказанном несоответствии направлению вылета/стволу |
| `SightsPointRear`, `SightsPointFront` | Точки, по которым считается прицельная линия | Если точки не соответствуют реальной прорези и вершине мушки |
| `SightsPosition` и `eye` | Базовая привязка прицеливания | При первоначальной настройке; затем фиксировать |
| `Range X` | Положение в анимации прицела | Для выбора физической позы целика на данной дальности |
| `Range Y` | Дальность, метры | Для обозначения режима пристрелки |
| `WeaponPosition.Offset` | Поправка положения оружия для данного режима | Чтобы камера оказалась на нужной линии |
| `WeaponPosition.Angles` | Угловая поправка для данного режима | Чтобы направление камеры согласовалось с этой линией |

Offset записывается в метрах, Angles — в градусах в порядке полей префаба. Эти поля нельзя приравнивать напрямую к мировым XYZ камеры: они проходят через цепочку ADS.

Для новой пушки нужны корректные узлы модели и `SightsComponent` с точками и диапазонами. Новая анимация и собственный генератор нужны только при недостаточности существующих. Для итоговых углов нашего АК74М существующей анимации хватило.

## 3. Резервная копия перед настройкой

1. Сохранить исходный `.blend`, экспортируемый FBX, XOB и его метаданные, основной префаб и префабы с локальными переопределениями прицела.
2. Записать SHA-256, GUID модели, цепочку родителей, все эффективные Range/Offset/Angles и Default Index.
3. Создать отдельную копию модели и тестовый префаб. Новая модель получает собственную идентичность ресурса; существующие `.meta` и instance ID не пересоздавать.
4. Выбрать один патрон, магазин и комплектацию. Зафиксировать баллистику на весь цикл настройки.
5. После каждого этапа сохранять небольшой diff и подтверждённый контрольный режим.

Изменение только одного режима не должно затрагивать соседние записи массива. Рабочие значения сохранять буквально, даже если новый расчёт отличается на доли миллиметра.

## 4. Подготовка модели в Blender

### Геометрия прицельной линии

Найти именно верхушку центрального столбика мушки и геометрический центр прорези целика. Защитные ушки мушки не являются точкой наведения. Измерять выбранные вершины, а не приблизительный центр объекта или Empty.

Проверить масштаб, трансформы объектов, Armature, rest-позу и веса. Не применять трансформы или менять оси уже связанного рига вслепую: это может изменить экспорт и bind-матрицы.

В нашем расчёте исходного FBX использовались:

- `rearSight_low`, вершины 14 и 15 — середина выбранных краёв прорези;
- `handle_low`, вершины 4271, 4273, 4274, 4275, 4277, 4278, 4279, 4280 — выбранная верхушка мушки;
- у этих вершин проверены веса соответственно `w_sight = 1` и `w_root = 1`.

Индексы относятся только к этой топологии. После изменения сетки точки выбрать заново.

### Шарнир целика

Определить центр и направление реального шарнира планки по геометрии. Сопоставить их с осью `w_sight` в одной системе координат. Проверять не только совпадение центров, но и направление оси: наклон оси может дать боковое движение при подъёме.

Исправлять сначала на копии. После правки bind-положения сохранить исходную геометрию в rest-позе и проверить деформацию на нескольких значениях анимации. В нашем процессе ось согласовали с шарниром, затем использовали существующий клип. Копирование оси из ванильного АК74 без привязки к нашей сетке не заменяет эту проверку.

### Полный скиннинг

Координата `mesh.vertices[i].co` сама по себе не является координатой точки после анимации. В Blender брать evaluated mesh через dependency graph, затем применять `evaluated_object.matrix_world` и переводить результат в систему координат оружия движка. Так учитываются Armature, bind-преобразования и веса.

Для использованного импорта перевод Blender → координаты расчёта движка менял местами Y и Z. Это проверенная конвенция данного импорта, не универсальное правило для любого FBX.

Сравнивать нужно точки, кости и направление ствола в одной системе. Ранний вывод о смещении прорези на 1.62 мм был ошибочным из-за смешения координат. Не использовать его как основание для правки модели.

### Узлы ствола и eye

Положение `barrel_chamber`, положение `barrel_muzzle` и их направления — разные величины. Линия между двумя узлами не обязательно совпадает с направлением их локальной оси и фактической начальной скоростью пули.

В нашей последовательности отдельно исправлялся наклон chamber на тестовой модели; после импорта пользователь подтвердил улучшение попаданий. На финальном этапе расчёта диапазонов chamber, muzzle, eye и баллистика уже были зафиксированы. Не повторять их выравнивание при каждой смене дальности и не переносить ствол на высоту прицела.

Все Empty не обязаны находиться на одном горизонте. Прицельные точки привязываются к реальным прицельным приспособлениям, узлы ствола — к стволу, крепления — к своим посадочным местам.

## 5. Экспорт и проверка загрузки

1. Экспортировать подготовленную копию отдельным FBX с нужной иерархией, костями, skin weights и узлами. Сохранить используемые настройки экспорта; не менять попутно материалы, масштаб и ориентацию.
2. Импортировать через Workbench и подключить полученный XOB только к тестовому префабу.
3. Проверить фактический GUID/путь `MeshObject.Object` у загруженного предмета.
4. Снять локальные матрицы `w_sight`, chamber и muzzle. Положение в окне Blender не доказывает, что движок загрузил этот вариант.
5. Для проверки брать свежий экземпляр. Открытый ресурс, объект в мире и предмет в руках могут содержать разные переопределения.
6. Переносить результат на основной префаб только после проверки тестового.

В доступной нам диагностике XOB были матрицы костей, но не прямое чтение отрендеренных вершин после скиннинга. Расчёт evaluated FBX нужно называть расчётом FBX, а совпадение в XOB подтверждать отдельно визуально и игровыми замерами.

## 6. Прицельные точки и наследование

У текущего АК74М:

```text
SightsPointFront:
  PivotID slot_ironsight_front
  Offset 0 -0.0002 0

SightsPointRear:
  PivotID w_sight
  Offset 0.00162 0.00672 -0.04815
```

Это локальные смещения относительно указанных pivots. Число 0.00162 не означает доказанный боковой уход видимой прорези на 1.62 мм. Нужно применить матрицу pivot и сравнить с геометрией в той же позе.

Для другой модели вычислять локальную точку из реальной геометрии: `p_local = inverse(T_pivot) * p_weapon`. Проверять её на 100 м, 200 м и крайних положениях. Точка на неподвижном root не будет следовать за анимированным целиком.

Проследить цепочку экземпляр мира → дочерний префаб → родитель → ванильный base. Переопределять существующие `SightsComponent`, `SightRangeInfo` и `PointInfo` по их instance ID. Новые ID вместо наследуемых могут создать дополнительные записи.

У нас API некоторое время показывал 33 записи при 11 в файле. В такой ситуации проверять одновременно эффективный массив, реально загруженный ресурс, локальные изменения экземпляра и кэш. Само число 33 не доказывает конкретную причину. Не удалять родителей ради уменьшения счётчика.

Итоговая структура основного АК74М: 11 записей, порядок `440, 100, 200, …, 1000`, `SightsRangesDefaultIndex 1`. Первый режим 440 м — отдельная боевая пристрелка. `_full` проверять отдельно: он может иметь собственные старые переопределения и не получить значения основного автоматически.

## 7. Почему генератор не дал готовый результат

В предоставленном API `WB_CalculateWeaponZeroingAnimationValue` возвращает значение источника анимации и выдаёт Offset/Angles; `WB_GetZeroingData` также выдаёт положение оружия для заданного угла и дальности. Поэтому генерация может менять и позу целика, и положение оружия.

Числа Range X вроде 0.628665 на 200 м были результатом расчёта генератора для его входных данных. Они не означают, что такая высокая планка физически правильна для нашей модели. Нужно проверять реальные точки, ось, направление вылета и ADS, а не принудительно принимать результат.

Таблица `0.1 → 100`, `0.2 → 200` из учебного примера связана с подготовленной для него анимацией. На нашей геометрии правильная поза 200 м получилась при `0.153456`.

Если требуется сохранить конкретную низкую позу, необходимо проверить, обеспечивает ли её реальная прицельная линия нужный угол относительно вылета. Offset/Angles не следует использовать как произвольную компенсацию заведомо неверной механической позы.

Не вызывать функции генератора как безусловно read-only диагностику: они могут менять трансформы. Генерацию проверять на копии и сравнивать весь массив до/после. Сохранение мира и Apply to prefab — разные операции; перенос на основной префаб выполнять осознанно.

## 8. Баллистика и расчёт движения целика

Использовать фактический патрон и данные движка. Зафиксировать ресурс пули, начальную скорость/направление и параметры, влияющие на полёт. Таблица реального 5.45 из интернета не заменяет параметры игрового PP.

В сохранённой нативной таблице для использованного патрона `aim_height_m` составлял 0.0914829 на 100 м и 0.365932 на 200 м; времена — 0.140438 и 0.280875 с. `aim_height` использован как вход компенсации в малоугловом расчёте. Это не измеренные попадания и не доказательство фактического падения на каждой дальности.

Для каждой позы θ вычислить реальную прорезь R(θ) и вершину мушки F после скиннинга. Линия — `normalize(F − R)`. В продольной плоскости с Y вверх и Z вперёд:

```text
s(θ) = (F.y − R(θ).y) / (F.z − R(θ).z)
h(θ) = F.y + s(θ) * (O.z − F.z) − O.y
```

O — начало вылета в той же системе, h — высота линии над ним. От рабочей базы 100 м сохранить калибровку:

```text
k = b − s100 − (h100 + H100) / 100
sD = (b − k − (F.y − O.y + HD) / D) / (1 + (O.z − F.z) / D)
```

b — наклон направления вылета/принятой оси chamber, HD — табличная компенсация на D. Найти θ, при котором `s(θ) = sD`, например делением интервала пополам. Это применённая у нас относительная малоугловая схема, сохраняющая рабочие 100 м, а не универсальная точная модель движка.

В абсолютной реконструкции оставалась угловая невязка около 0.15077°. Её сохранили относительно проверенной основы, а не объявили устранённой. Для другой пушки сначала получить свою контрольную пристрелку и проверить соответствие chamber реальной начальной скорости; эту калибровку не копировать.

## 9. Как получить Range X из нужного угла

Нужна кривая существующей анимации, а не линейная пропорция между двумя произвольными режимами. В использованном `w_rfl_ak74_erc_sight.anm` были 11 кадров, ключи `w_sight` на кадрах 0, 3, 6, 8, 9, 10:

| Кадр | Угол из quaternion, градусы |
|---:|---:|
| 0 | 0 |
| 3 | 1.640208 |
| 6 | 4.129261 |
| 8 | 6.595742 |
| 9 | 8.339165 |
| 10 | 11.430060 |

На соответствующем участке обратить кривую и получить источник анимации. Для целевого угла около 0.839° получилось `Range X 0.153456`; нативная матрица дала около 0.838998°. Ранние цели 3.29472° и оценка X≈0.1425 не входят в итоговую методику.

Для остальных дальностей угол доходил примерно до 7.440°, что укладывалось в существующий клип. Своя анимация нужна, если требуемая траектория/ось/ползунок не воспроизводятся существующей или нужная поза выходит за пределы клипа. Доступность угла сама по себе ещё не проверяет контакт ползунка с планкой.

## 10. Расчёт Offset и Angles по ADS

Поза целика выбирается первой. Затем для неё рассчитываются Offset и Angles конкретного режима; базовые eye и SightsPosition остаются фиксированными.

Нужно снять в одном кадре после привязки камеры к кости:

- финальную мировую матрицу камеры и оружия;
- матрицу камеры относительно оружия;
- `w_sight`, chamber, muzzle, front/rear и SightsPosition;
- текущие Range и WeaponPosition;
- zeroing-матрицу, угловые и линейные модификаторы ADS;
- признак завершённого ADS, номер кадра и фактический ресурс предмета.

В нашей диагностике для этого использовались метки `AK74_ADS_FINAL_V3`, `AK74_ADS_PRECISE_V4` и `angular_v2`. Матрица до финальной привязки камеры к кости оказалась недостаточной. Пустой itemPrefab также не означал отсутствие АК74М: идентификацию пришлось дополнять моделью и выводом причины пропуска.

Алгоритм обратного расчёта:

1. Привести все точки и трансформы к координатам оружия: `T_camera_weapon = inverse(T_weapon_world) * T_camera_world`.
2. Вычислить `d = normalize(F − R)` по геометрии выбранной позы.
3. Выбрать точку камеры C на продолжении линии R–F назад, сохранив глубину исходного SightsPosition. В нашем расчёте: `C = R + d * ((SightsPosition.z − R.z) / d.z)`.
4. По однокадровым матрицам восстановить преобразование ADS, отделив текущие угловые/линейные модификаторы. Не складывать мировые Euler-углы с локальными Angles.
5. Численно подобрать Angles, чтобы forward финальной камеры совпал с d. Затем решить Offset для положения C в той же цепочке.
6. Проверить результат на нескольких кадрах и уже подтверждённых режимах. Для текущего АК74М использовались шесть точных кадров 100/200 м; контрольная разница модели составила до 0.018 мм по Offset и 0.00065° по Angles.
7. Записать кандидат только в нужную запись диапазона, проверить видимую ровную мушку и попадания в игре.

В нашем офлайн решателе использовалась восстановленная зависимость с коэффициентом 1.4 в одном из линейных модификаторов. Это особенность данной реконструкции ADS, не общий коэффициент для префабов. Для воспроизведения на другом оружии заново измерять цепочку, а не подставлять эту константу без проверки.

Совпадение мушки с целиком и совпадение попадания с точкой наведения — два отдельных критерия. Удачный Offset не заменяет проверку траектории, а правильные попадания не оправдывают кривую картинку прицела.

## 12. Порядок проверки в игре

1. После импорта/компиляции проверить загруженную модель и эффективные диапазоны у свежего экземпляра.
2. На 100 м проверить вершину мушки относительно прорези по горизонтали и вертикали, затем среднее попадание нескольких выстрелов по измеренной дистанции.
3. Повторить на 200 м. После их подтверждения зафиксировать обе записи и рассчитывать остальные относительно этой базы.
4. Последовательно проверить остальные режимы и отдельно 440 м; переключение режима должно давать согласованные движение целика и изменение ADS.
5. Проверять обычный и `_full` отдельно, включая локальные overrides мира. Не переносить автоматически старые данные из `_full` в основной.
6. Если нужно уточнение, разделить ошибку изображения и ошибку попадания; менять только ответственную часть одного режима.
7. Сохранить итог, хеши и сведения о проверке. Повторная генерация может перезаписать ручной результат, поэтому сначала копия и сравнение.

После завершения временные диагностические классы были закрыты флагом `ARMST_ENABLE_AK74_TEMP_DIAGNOSTICS`, оставленным неопределённым. Проверить успешную перекомпиляцию и отсутствие новых диагностических сообщений. Диагностика не должна постоянно работать в итоговой сборке.

## 13. Ошибки которые не нужно повторять

| Симптом или действие | Правильная проверка |
|---|---|
| Генератор высоко поднимает целик | Сравнить реальную линию, точки, ось и ADS, не объявлять Range X эталоном |
| На 100 хорошо, на 200 мушка уходит | Проверить позу и WeaponPosition именно 200 м; не двигать общий eye |
| Мушка совпадает, пуля выше | Снять фактическую начальную скорость и сравнить с линией прицела; не двигать геометрию без основания |
| Кажется, прорезь смещена на миллиметры | Учесть полный Armature и единое пространство координат |
| В файле 11 диапазонов, API видит больше | Проверить IDs, родителей, экземпляр и загруженный контейнер |
| Хочется всем диапазонам поставить нули | Сохранить позы и рассчитать индивидуальные Offset/Angles |
| Хочется скопировать ванильный АК74 | Перенести метод проверки, но пересчитать под наш шарнир и сетку |
| Нужно исправить только один режим | Не менять общую модель, eye, chamber, баллистику и подтверждённые записи |

Проблема бонусов приклада/цевья (`override stats failed to set`) относится к отдельному механизму модификаторов. Её исправление не является частью этой методики и на дату фиксации отложено.
